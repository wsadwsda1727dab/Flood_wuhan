## 1. 目标与范围

在 GEE Code Editor 中用 **Sentinel-1 变化检测 + Sentinel-2 光学证据**，为武汉市 2016–2025 年的 **19 场暴雨/洪涝事件**生成伪标签，并按事件分层抽样导出随机森林（RF）训练样本 CSV，供后续多年份洪涝制图实验使用。

| 项目 | 内容 |
|---|---|
| 研究区 | `projects/studied-glow-475306-v5/assets/wuhan` |
| SAR | `COPERNICUS/S1_GRD`（IW、VV+VH） |
| 光学 | `COPERNICUS/S2_SR_HARMONIZED`（L2A 优先）→ `COPERNICUS/S2_HARMONIZED`（L1C 回退） |
| 辅助 | `USGS/SRTMGL1_003`（DEM/坡度）、`JRC/GSW1_4/GlobalSurfaceWater`（永久水体） |
| 事件表 | `doc/2016_2025.docx`（19 个暴雨时段，含起止时间、影响区、雨量） |
| 输出 | 合并样本 CSV、每事件样本 CSV、每事件汇总 CSV（Google Drive） |

## 3. 主流程（以 pseudo_labels1 为准）

1. **事件循环**：`EVENTS`（**18 个时段**，【改动28】把 2024 年的两场并成一场）→ `buildEvent(ev)` 逐个执行；`RUN_EVENT_NAMES` 可只跑指定时段。脚本加载时先跑一次【改动29】的 S2 后窗越界自检。
2. **窗口推导**（`eventWindows`）：事件时间是北京时间，`bjToUTC` 换算成 UTC；**【改动24】后窗口已按传感器拆成两个**（S1 与 S2 都取 18 天）。
   - 前窗 = 事件开始 − `PRE_GAP_DAYS`(5) − `PRE_WINDOW_DAYS`(24) ~ 事件开始 − 5 天
   - S1 后窗 = **事件结束** ~ 事件结束 + `S1_POST_PAD_DAYS`(18)（只做搜索，实际合成仍是"最早 S1 之后 8 天"）
   - S2 后窗 = **事件结束** ~ 事件结束 + `S2_POST_PAD_DAYS`(18)
   - 事件表里的 `preStart/preEnd` 照旧作用于前窗，`postStart/postEnd` 现在**只作用于 S1**；S2 可用新增的 `s2PostStart/s2PostEnd` 单独指定
     - **【改动25】`2020_0628` 手工截断**：截到 `2020-07-05 00:00`（约 5.5 天）——因为下一场暴雨落在它默认的 18 天后窗里，max 口径会把下一场的水并进本场。
     - **【改动28】`2024_0621_0628` 是唯一的窗口特例**：`s2PostEnd: '2024-07-16 00:00'` → S2 后窗 **24 天**（两场默认窗口之并）。原 `2024_0621` 截到 06-28 后只剩 5 景且全被云盖（S2 覆盖 0.3%），已改为合并处理。
3. **S1 前时相**：`post/pre` 双窗口取 `filterBounds` + IW + VV/VH → `dropFill` 去除切片填充值 → `median()` 作为基线。
4. **S1 后时相**：取"事件后最早 8 天"的影像（跨 orbit 40 与 113，掩膜并集才盖满研究区）→ `dropFill` → **逐景去偏** → `median()`。
5. **差值**：`VV_diff = 后 − 前`、`VH_diff = 后 − 前`（用去偏后的后时相）；`VV_ratio` 仍由原始绝对后向散射算，保持物理可解释。
6. **有效像元**：`s1Valid` = 前后时相 VV/VH 四个掩膜取交集，只有这些像元参与判识。
7. **S2 光学【改动25/26/30】**：S2 后窗（事件后 18 天，合并事件为 24 天）的 L2A（无则 L1C）→ `QA60` 云掩膜 → 云量 ≤ 90% → **逐景先算 `NDVI`/`MNDWI`，再在时间维取统计量**（`S2_INDEX_STAT`：`'max'` / `'median'`）；`S2_Valid` 恒由每景"云掩膜后仍有观测"的 0/1 指示带取 **max**（【改动26】已与统计量解耦）。**【改动30】** 事件表可用 `ev.s2Source = 'L1C' / 'L2A'` 强制指定源（不写则沿用"L2A 优先"自动选择）。旧口径是"先对波段取中值、再算指数"，本版已废弃。
8. **判识**：
   - SAR 洪水候选 `sarFlood01` = `VV_diff < -4.0` ∧ `VH_diff < -3.5` ∧ `s1Valid`
   - High Flood = 候选 ∧ 光学水 ∧ 非永久水体 ∧ 低坡度
   - Medium Flood = 候选 ∧ 无 S2 ∧ 非永久水体 ∧ 低坡度
   - 非洪涝 = SAR 稳定区（`|diff − 中位数| < 1.5 dB`）∧ 非永久水体 ∧ 低坡度（±光学非水）
   - 冲突保护：同时进入正负类时优先保留洪水 → `label`（0/1，Unknown 被掩膜）+ `conf_flood`/`conf_nonflood` 分带
9. **抽样**：`stratifiedSample`，`classPoints = [min(2000, 负类像元), min(2000, 正类像元)]`，scale 100 m，seed 42，样本带 `event_id/year/storm_*` 属性。
10. **导出**：合并样本 CSV、每事件 CSV、每事件汇总 CSV；`selectors` 固定列序（避免列错位）。

## 5. 版本演进：每个版本新增了什么

### temp.original.js → temp.js：从单事件到 19 事件

把写死在函数里的窗口改成按事件推导，并补齐可用性判断。主要增量（脚本内以【改动 N】标注）：

- 【改动1】事件表 19 个时段；【改动2】时间窗口工具（北京时 → UTC）；【改动3】`buildEvent(ev)` 逐事件化
- 【改动4】数据可用性检查（缺 S1 就跳过该时段）
- 【改动5】新增 `s1Valid`：前后时相都有观测的像元才参与判识，避免把"无 SAR 数据"当成稳定区/非洪涝
- 【改动6】S2 改为 L2A 优先、无则回退 L1C，并加云量过滤（原版 2016 年完全拿不到 S2）
- 【改动7】删除外部模块依赖（Otsu 结果原本并未进入判识，却给每个时段加了一次外部依赖）
- 【改动8】正负样本冲突保护 + `conf_flood`/`conf_nonflood` 置信度分带
- 【改动9】像元统计合并为一次 `reduceRegion`（原来 3 次）
- 【改动10】分层抽样按实际像元数动态取 `min`
- 【改动11】样本带 `event_id/year/storm_*` 属性
- 【改动12】逐时段执行 + 每时段汇总表；【改动13】导出拆成合并/每事件/汇总三份
- 【改动14】Map 只显示一个时段（避免 19×10 个图层）；【改动15】`RUN_EVENT_NAMES` 支持只跑部分时段

### temp.js → temp1.1.js：后窗口语义修正 + 日期精化

- 【改动1（用户改）】后窗口起点从「事件开始 − 6 天」改为 **事件结束**，`POST_PAD_DAYS` 6 → **18 天**（覆盖 12 天重访 + 余量）
- 【改动16】日期打印**带上时刻**（北京时 `YYYY-MM-dd HH:mm`），并补上 S2 的日期 —— 原先只到天，同一天的影像分不出事件前后
- 【改动17】新增**后时相审计**：`s1_post_after_count` / `s1_post_after_dates`，并在"后窗口有影像但没有一景晚于事件结束"时打印警告

### temp1.1.js → temp1.2.js：后时相覆盖修复（用户改）

- 后时相从「整个 18 天窗口中值」改为「**事件后最早 8 天**（跨两条轨道）中值」，并把填充值掩掉：`.map(function (im) { return im.updateMask(im.gt(-50)); })`
- 起因：担心 18 天窗口把"已经退水"的影像混进来；同时单日窗口只能覆盖武汉约一半

### temp1.2.js → temp1.3.js：填充值统一、去偏、QC 字段、导出修正

- 【改动18】填充值过滤抽成 `dropFill(im)`（阈值 `S1_FILL_DB = -50`），**前时相也用**——前窗两条轨道各 4 景，某些像元可能只有一条轨道有数据
- 【改动19】整幅去偏（双差分，`DEBIAS = true`）：扣掉有效区内的中位偏移，使阈值含义从"比前窗基线低 4 dB"变成"比本事件典型变化再低 4 dB"
- 【改动20】`s1_valid_cover` / `vv_offset_db` / `vh_offset_db` 写进汇总表
- 删除 A/B/C 三段临时诊断（每个事件少 3 次请求）

| 2 | 汇总行（4.15 节） | 新增 `n_valid_px` / `s2_cover_valid_frac`（S2 有效 ÷ SAR 有效）/ `high_flood_share`（High ÷ 正样本）/ `s2_qc_flag`；命中阈值时打印警告 |
| 3 | 全局参数 | 新增 `LOW_S2_COVER_MIN = 0.5`、`MIN_HIGH_FLOOD_SHARE = 0.3`、`NO_OPTICAL_COVER = 0.05` |
| 4 | `SUMMARY_SELECTORS` | 4 个新列插在 `valid_area_km2` 与 `sample_count` 之间；`summaryBase` 同步补 null 字段（跳过的事件也保留列） |

**标记规则**：`NO_OPTICAL`（覆盖率 < 5% 或 High 占比 = 0）＞ `LOW_S2_COVER`（覆盖率 < 50% 或 High 占比 < 30%）＞ `OK`。

**设计取舍**：`status` 列**不改**（仍是 `OK` / `NO_SAMPLE` / `SKIPPED_NO_S1`），质控结果单独一列，这样 `Summary`~`Summary8` 在 `status` 上仍可直接对照——旧文档里"全部 status=OK"的说法也依然成立。

**按 `Summary8` 数据回算**：11 场 `OK`、6 场 `LOW_S2_COVER`（`2016_0601` / `2016_0630` / `2017_0608` / `2018_0518` / `2020_0628` / `2024_0628`）、2 场 `NO_OPTICAL`（`2017_0824` / `2024_0621`）——与人工判定完全一致。其中 6 场 `LOW_S2_COVER` 与基线状态一致（2016–2018 只有 L1C、云、截断、SAR 覆盖限制），不是本次改动引入。

**注意**：改动27 只让问题**可见**，不改任何标签数值。`2017_0824`、`2024_0621` 仍需实际处置（`2024_0621` 取消 S2 后窗截断或剔除；`2017_0824` Console 核对 S2 源后强制 L1C 或剔除）才能用于训练；修复后重跑会再产出一版 `Summary`（`RUN_EVENT_NAMES` 已需改回 `null`）。

**静态校验**：`node --check` 通过；用 `Summary8.csv` 的 `s1_valid_cover × ROI` 复算 `s2_cover_valid_frac` 与 `high_flood_share`，标记结果与人工判定逐行一致。

### pseudo_labels1.js【改动28】：合并 2024 年两场暴雨（事件数 19 → 18）

**问题**：`Wuhan_2024_0621`（6/21–22，100 mm）与 `Wuhan_2024_0628`（6/28，147.8 mm）相隔 7 天。原来两场独立，并给前者手工截断 S2 后窗到 06-28（【改动25(c)】）以躲开后者——结果 06-22~06-27 只剩 5 景且几乎全被云盖，`Summary8` 里该场 `s2_cover_valid_frac = 0.3%`、`n_high_flood_px = 0`、面积虚涨 +150%。

**为什么不能简单地"取消截断"**：

| 项 | `2024_0621` 默认窗口 | `2024_0628` 默认窗口 |
|---|---|---|
| S2 后窗（UTC） | 06-21 23:00 ~ **07-09 23:00** | 06-28 04:00 ~ 07-16 04:00 |

两窗重叠 **11.8 天 = 各自窗口的 65.5%**，而重叠段恰好是第二场暴雨的时段。逐景 max 取峰值 → 同一批像元被两个事件重复打标（标签混淆），若两场分处训练/验证两侧还会造成**训练集泄漏**。而且 `2024_0621` 的截断点（06-27 16:00 UTC）距第二场暴雨起点（06-27 19:00 UTC）只剩 **3 小时**，没有"延一点"的空间。

**改法**：合并为一场 `Wuhan_2024_0621_0628`：

| # | 项 | 取值 / 说明 |
|---|---|---|
| 1 | `start` | `2024-06-21 07:00`（首场起点） |
| 2 | `end` | `2024-06-22 07:00`（**首场终点**，不是次场终点） |
| 3 | `s2PostEnd` | `2024-07-16 00:00`（北京时）→ S2 窗口 = 两场默认窗口之并，**24 天**（唯一特例） |
| 4 | `rainRefMM` | `247.8`（两场站点最大值之和，站点不同，须在方法里注明） |
| 5 | 前窗 | 不写死，由 `start` 推导 = `2024-05-22 ~ 2024-06-15`，**早于两场暴雨** ✓ |

**为什么 `end` 取首场终点**：`end` 决定 SAR 后时相合成的起点（`t0` = 最早的后时相 S1，合成跨度 `[t0, t0+8 天]`）。取首场终点才能让 8 天跨度有机会同时覆盖 06-28 的次场；若取次场终点（06-28 12:00），后时相全部晚于次场，首场的积水面会被整体丢掉。

**已知局限（欠检而非误检）**：合并后 SAR 后时相仍从 06-22 起算，8 天跨度若只覆盖到次场的一部分，则"只在首场积水、之后已退"的像元会漏检。这类漏检表现为**面积偏小**，不会把没水的地方标成水（因为 SAR 下降门槛仍必须满足）。重跑后需核对本行的 `s1_post_after_dates` / `s2_count` / `s2_qc_flag`。

### pseudo_labels1.js【改动29】：相邻暴雨 S2 后窗越界自检（启动时跑一次）

**背景**：`2020_0628` / `2024_0621` 都是靠**手工** `s2PostEnd` 躲开下一场暴雨的。"靠人记得"的约束必然有漏网：核查发现 **`2025_0522` 的 S2 后窗（止于 2025-06-09）已经伸进 `2025_0607` 的暴雨时段（起于 2025-06-07），重叠 2.7 天**，此前无人察觉。

**改法**：新增纯 JS 函数 `reportS2WindowOverlaps()`，在 `EVENTS_TO_RUN` 之前调用（不连 GEE、不产生额外计算）。逐对比较"另一场的暴雨起点是否落在本场 S2 后窗之内"，命中就打印事件名、窗口终点、重叠天数，并提示两种处置（给前一场指定 `s2PostEnd`，或把两场合并）。

**实际输出（改动28 落地后）**：

```
⚠ 【改动29】S2 后窗越界自检：发现 1 处与下一场暴雨重叠……
   · Wuhan_2025_0522 的 S2 后窗（止于 2025-06-09）与 Wuhan_2025_0607（起于 2025-06-07 00:00）重叠 2.7 天
```

`2020_0628`（已手工截断）与 `2024_0621_0628`（已合并）都不再命中，说明自检结果与人工判定一致。

**待定**：`2025_0522` 是否要截断需先看该窗口的 `s2_count` 与清晰景分布——**不能盲截**，否则会重演 `2024_0621` 的"截完就 NO_OPTICAL"。它目前是 B 类（仅验证），暂可不动。

### pseudo_labels1.js【改动30】：事件表可强制指定 S2 源（`ev.s2Source`）

**背景**：`Summary8` 里 `2017_0824` 的 S2 源从 `S2_HARMONIZED(L1C/TOA)` 翻成了 `S2_SR_HARMONIZED(L2A)`（景数 9→10），而该 L2A 在窗口内几乎全无效：S2 覆盖 **98.0% → 1.3%**、`n_high_flood_px` 归零、面积虚涨 +230%。只要窗口内出现**个别** L2A 景，整场就被换到另一套辐射口径——这类问题必须能手工压回。

**改法**：源选择块前加一个可选覆盖：

```javascript
var forcedS2 = ev.s2Source ? String(ev.s2Source).toUpperCase() : null;  // 'L1C' / 'L2A'
if (forcedS2 === 'L1C') { s2Source = 'S2_HARMONIZED(L1C/TOA)'; s2Col = s2l1cCol; }
else if (forcedS2 === 'L2A') { ... }
else if (avail.s2_sr_count > 0) { ...原自动逻辑... }
```

命中的事件会打印一行说明（含本窗口的另一个源的景数，便于判断是否值得改回）；若强制指定的源在本窗口 0 景，再打印一条警告。

**落地配置**：`Wuhan_2017_0824` 设为 `s2Source: 'L1C'`，恢复基线行为（L1C、覆盖 98.0%、High 占比 93.7%）。**仍需在 Console 核对本行的 `s2_sr_count` / `s2_l1c_count`**：若确认该窗口确实有可用的 L2A 覆盖，删掉这一行即可改回自动选择。

**静态校验（改动28/29/30）**：`node --check` 通过；用假 `ee` 抽出 `bjToUTC` / `eventWindows` / `reportS2WindowOverlaps` 与真实 `EVENTS` 跑了一遍——事件数 18、`Wuhan_2024_0621_0628` 的窗口为"前窗 05-22~06-15 / S1 后窗 06-21~07-09 / S2 后窗 06-21~07-16（24 天）"、越界自检命中 1 处（`2025_0522`↔`2025_0607` 2.7 天）、`2017_0824` 打印 `[s2Source=L1C]`。

### pseudo_labels1.js【改动31】：越界尾段的"晴空贡献"诊断 + 默认改回全量

**问题**：【改动29】只能回答"越界了没有"，回答不了"要不要截"。而 `2024_0621` 的教训恰恰是"截了反而更糟"——它被截到 6 天后只剩 5 景且全被云盖，S2 覆盖掉到 0.3%、High Flood = 0。判断依据不可能是 `s2_count`：该列 = `s2_sr_count + s2_l1c_count`（同一批 acquisition 在 L2A / L1C 各算一次），只反映集合大小，与"晴空"无关。

**改法**：两处。

1. 把【改动29】的判定抽成可复用函数 `s2WindowOverlapHits(ev)`（返回 `[{name, startMs, startStr, overlapDays, s2StartMs, s2EndMs}]`），启动自检与事件内诊断共用同一条判定；`reportS2WindowOverlaps()` 改为调用它，输出文字与原来一致。
2. 在 4.5b 加诊断（开关 `S2_TAIL_DIAG`，默认 `true`）：对命中的事件把 S2 后窗切成"截断段 `[s2PostStart, 后一场起点)`"与"尾段 `[后一场起点, s2PostEnd)`"，各取一次逐景 `S2_Valid` 的 max 并集，一次 `reduceRegion` 取回 5 个量（口径与 `s2_valid_px` 相同：`sum`、`scale = SAMPLE_SCALE`、`geometry = geom`）：

| 量 | 含义 |
|---|---|
| `n_window` | 整窗有效像元（= 写进 summary 的 `s2_valid_px`） |
| `n_head` | 截到后一场起点之前剩下多少 |
| `n_tail` | 尾段自己的并集 |
| `n_tail_excl` | **只在尾段有效**（= 截掉就丢的光学证据） |
| `n_head_excl` | 只在截断段有效 |

**判读规则**：`n_tail_excl ÷ n_window` ≤ 5% → 可以安全截（给本场指定 `s2PostEnd` 到后一场起点之前）；> 5% → 不要截，按【改动28】合并两场。

**为什么默认开**：只有命中的事件会打印（`2025_0522` 截断后**当前 0 场命中**；下次再出现相邻暴雨越界时会自动打印），其余事件零额外开销；不想看时置 `S2_TAIL_DIAG = false`。

**静态校验（未连 GEE）**：命中判定与【改动29】一致——`Wuhan_2025_0522` 的 S2 后窗 `2025-05-22 ~ 2025-06-09`（18 天）与 `Wuhan_2025_0607`（起于 `2025-06-07 00:00` 北京时 = `2025-06-06 16:00` UTC）重叠 **2.67 天**；可截段 15.33 天、尾段 2.67 天；合并场 `2024_0621_0628` 与其余 16 场都不命中。`node --check` 通过。

**实测（`doc/labelConsole2.md`，2026-09-24 单跑 `['Wuhan_2025_0522', 'Wuhan_2017_0824']`）**：

- `Wuhan_2025_0522` 的诊断输出：整窗 **755,178** 有效像元 / 截到后一场起点之前 **750,734** / **只在尾段有效 4,444 px = 0.6%** / 尾段总有效 11,732。尾段那 4 景（06-07 的 L1C、L2A 各 2 景）几乎全被云盖 → **判定"可以截"**。
  - （诊断的 `n_window` 755,178 与汇总列 `s2_valid_px` 755,215 差 37 px = 0.005%：两者是两次独立的 `reduceRegion`，属正常数值噪声；判读只看比例，不看绝对差。）
- **落地**：`EVENTS` 里给 `Wuhan_2025_0522` 加 `s2PostEnd: '2025-06-07 00:00'`（北京时 = `2025-06-06 16:00` UTC），S2 后窗 **18 → 15 天**（`2025-05-22 ~ 2025-06-06`）。截掉的是 06-07 那 4 景；它们也不属于 `Wuhan_2025_0607` 的后窗（那场从 06-08 16:00 UTC 起算），所以不会让另一场丢观测。
  - 截断后【改动29】自检从"命中 1 处"变为"未发现相邻暴雨窗口重叠"（0 处），【改动31】诊断也不再触发（无重叠可诊断）。**副作用**：这条诊断报告本身会消失；日后若要复核"截断是否仍然安全"，需临时删掉 `s2PostEnd` 再跑一次。
  - **`Summary9` 里 `Wuhan_2025_0522` 的那一行因此过期**（是 18 天窗口的结果）：重跑后 `s2_post_window_utc` 变 `2025-05-22 ~ 2025-06-06`、`s2_post_days` 18 → 15、`s2_valid_px` 约 −4.4k（覆盖 86.5% → ~85.9%），标签小幅变化。
- `Wuhan_2017_0824` 的 Console：`【改动30】S2 数据源被事件表强制指定为 L1C（本窗口 L2A 景数 = 1）`；`avail` 里 **`s2_sr_count = 1`**（唯一一景 `2017-08-28 11:09`）、**`s2_l1c_count = 9`**（`2017-08-26 11:14` ×4 + `2017-08-28` ×5），合计 `s2_count = 10` 与 CSV 一致。**结论：保留 `s2Source: 'L1C'`** —— 单景 L2A 正是旧自动选择下"S2 覆盖只有 1.3%、High = 0"的来源；强制 L1C 后覆盖 98.0%、High 94.4%。

| 越界尾段的晴空贡献（【改动31】） | 回答"越界了要不要截" | 判据：`n_tail_excl ÷ n_window` > 5% 不能截（会丢光学证据），≤5% 才能安全截。**实测 `2025_0522`：整窗 755,178 / 只在尾段有效 4,444 px = 0.6%** → 判定"可以截"，已在事件表加 `s2PostEnd: '2025-06-07 00:00'`；截断后自检命中数 1 → 0 | 保留（命中才打印；截断后当前无命中） |

## 7. 已验证的关键结论（含数值）

1. **前后时相可得性**：19 个事件在修正后窗口下都有事件前/后影像；前时相全部早于事件开始。
2. **单日 vs 多日覆盖**：只用事件后最早一天，`s1Valid` 覆盖率仅 **0.46**（后时相只覆盖武汉东部与北部）；改为"最早 8 天、跨两条轨道"后覆盖率 **= 1.00**。
3. **GRD 填充值**：切片无数据区的填充值是**很大的负值**（`mask()` 报告为有效），必须用 `dropFill` 显式掩掉，否则会产生 −30000 dB 量级的假变化。
4. **背景漂移真实存在**：同轨道相隔 12 天、无洪水期，orbit 40 ≈ 0、orbit 113 ≈ −1.1 dB → 漂移由天气（干湿）驱动，与几何无关。
5. **事件期偏移与轨道有关**：2025_0607 事件期 orbit 40 ≈ +1.28~+1.75 dB、orbit 113 ≈ +0.25~+0.63 dB，`offset_spread_db ≈ 1.06 dB` → 全局扣一个数会在两条轨道覆盖区残留 ±0.5 dB 偏差（沿轨道条纹），必须逐景去偏。
6. **阈值敏感性（同一模式内）**：每 0.5 dB 约 −15%，`flood_sens_ratio ≈ 1.42`（=−3.5 档 ÷ −4.5 档）。此前"0.75 dB 造成 52% 差异"的说法是**跨模式**比较（none/global/perImage），不是纯阈值敏感性。
7. **2025_0607 洪涝像元随处理方式的变化**：234（单日后窗口）→ 887（`none`）→ 1347（`global`）→ **1366（`perImage`，含残差归零）**。`perImage` 落在 `none` 与 `global` 之间，符合"对 orbit 40 多扣、对 orbit 113 少扣"的预期。
8. **样本类别比例**：该事件从 2000 : 234 改善到 2000 : 1347（global）；正类像元数低于 2000 时按全量入样，无需再调抽样参数。
9. **S2 口径跨年不一致**：2016–2018 的事件多走 L1C/TOA（2018 两个事件甚至 L1C 有 8/22 景而 SR=0），2019 年起稳定走 SR/L2A → 跨年混训需按 `s2_source` 分层。
10. **事件定义存疑**：`Wuhan_2025_0607` 的雨量注记写的是"新洲张渡湖站 117.2 mm（**6 月 21 日**数据）"，而事件窗口是 6 月 7–9 日，需回查 `doc/2016_2025.docx`。
11. **QC 的 sum/count 口径差别**：`sum` 是面积加权像元数（部分覆盖的网格按比例计入），`count(selfMask())` 数的是"至少含一个洪水像元的网格数"，同事件 1200.35 vs 2001。标签与 QC 必须同口径。
12. **面积口径**：`valid_area_km2` 与武汉官方面积吻合（8,581.57 vs 8,569 km²，差 0.15%）；`n_flood_px × 0.01` 系统性偏大约 16%（比值 0.86），面积报告一律用 `flood_area_km2`。
13. **perImage 残差**：逐景校正后复合仍留 +0.25 dB 残差（4 景逐像元取中值是非线性组合），已在本版扣除。
14. **全量 19 事件结果**：全部 `status=OK`、无 skipped；洪涝面积与雨量的一致性跨度为 34 倍（每 100 mm 雨量对应 1.2 ~ 41.4 km²）→ 各事件标签不可直接混用，详见 `csvdata/事件筛查与训练集划分.md`。
15. **机制发现**：洪涝面积的上限主要由"S2 在事件后窗口是否测到水"决定，而非 SAR 阈值——4 个低面积事件（2021_0823、2022_0627、2023_0618、2023_0719）的 `n_medium_flood_px = 0`、S2 全域有效，且放宽阈值到 −3.5 dB 面积只增 4%~23%。→ 这条结论先催生【改动24】（S2 窗口收到 5 天），**实跑后证明方向不对**：问题不是退水而是云。**【改动25】改为"保持 18 天窗口 + 逐景算指数取 max"**，4 个低面积事件的 High 回升 +37%~+752%，极差 17.38→5.63 倍，见第 5 节末。
16. **口径敏感性（【改动26】前后各一次配对）**：18 天档把统计量从 `max` 换成 `median`，面积降到 `Summary6` 的 0.11~0.40（覆盖没变的三场），而 `Summary7` 与 18 天档基线偏差 ≤14%（`2022_0627` 1.9287 vs 1.9287 km²）→ **"逐景算指数"与"波段级合成"在中心量口径下几乎等价，`Summary6` 的增益全部来自 max 统计量**；标签面积被口径主导，论文必须写明"事件后 18 天峰值并集"。配套修复见【改动26】（`S2_Valid` 与统计量解耦）。
17. **修复后全量跑（`Summary8`）**：改动26 对 `'max'` 档是**严格 no-op**——5 个对照事件与 `Summary6` 逐字段 0 差异；19 行 `status` 全 `OK`，行内自洽性（high+medium=flood、两类 non-flood 求和、sens_ratio）全部通过。但暴露 2 场"光学证据几乎为零"的事件：`2024_0621`（0.3%、面积 +150%）与 `2017_0824`（1.3%、面积 +230%），两场 `n_high_flood_px = 0`、正样本 100% 是 Medium。→ 全量一致性 16.0 倍/ρ=0.22（基线 33.59/0.26）；剔除这两场后 10.6 倍/0.47。**结论：`Summary8` 可替代基线作为全量版本，但不能直接用于训练**，须先处置这两场。配套质检【改动27】。
18. **相邻暴雨的窗口重叠是系统性风险，不是个案**：`2024_0621` 的 S2 后窗若恢复默认，会与 `2024_0628` 重叠 11.8 天（占各自窗口 65.5%）；而它当前的截断点距第二场暴雨起点只剩 3 小时 → 没有"延一点"的空间。同时自检还查出 **`2025_0522` 的窗口伸进 `2025_0607` 的暴雨 2.7 天且从未察觉**。→ 结论：单场截断救不了 `2024_0621`（那几天全被云盖），正确处置是**合并为一场**（【改动28】）；并且"是否越界"必须由【改动29】自检而不是靠人记。另外 `2017_0824` 证明"窗口内出现个别 L2A 景"会把整场拖去另一套辐射口径，故加【改动30】强制源开关。合并后事件数 19 → **18**。
19. **处置后全量重跑（`Summary9`，18 事件）**：`NO_OPTICAL` 清零（`OK` 13 / `LOW_S2_COVER` 5），`2017_0824` 回到 98.0% 覆盖 / 94.4% High / 21.9 km²·100mm⁻¹，合并场 `2024_0621_0628` 覆盖 80.0% / High 32.2%（且 `s1_valid_cover` 从 0.465 顺带修到 1.000）。跨事件一致性同时改善：极差 **15.99 → 10.63 倍**、ρ(雨量,面积) **0.22 → 0.58**（基线 0.26）。→ v1 里"口径修正只收窄极差、不提升秩相关"的说法要订正：那是 2 场坏标签（`2017_0824` 63.8、`2024_0621` 62.6 km²/100mm）把 ρ 压下去造成的，处置后 ρ 明显回升。
20. **两场单事件 Console 复核（`doc/labelConsole2.md`，2026-09-24）**：① **越界尾段**——`2025_0522` 整窗 755,178 有效像元，其中"只在尾段（06-07 的 4 景）有效"仅 **4,444 px = 0.6%**，尾段自身有效 11,732 px（≈ 98% 被云盖）→ **可截**，已落地 `s2PostEnd: '2025-06-07 00:00'`（18 → 15 天），自检命中 1 → 0 处。这条把"越界到底要不要处理"从"靠人猜"变成了"看一个比例数"。② **S2 源**——`2017_0824` 的 `avail` 是 `s2_l1c_count = 9` / `s2_sr_count = 1`（唯一那景 L2A 在 `2017-08-28 11:09`），单景撑不起窗口，**强制 L1C 的处置成立**。

## 10. 附：过程中形成的两个"教训"

1. **GEE 影像算术会丢属性**（`system:time_start` 也会丢）。凡是要在生产影像上读时间/轨道等属性，必须在运算后显式 `.set()` 带过去。
2. **`Export.table.toDrive` 不写 `selectors` 时列序不可靠**：表头与取值可能不一一对应（曾出现 `conf_nonflood` 列里全是事件名、`slope` 列里全是日期）。固定 `selectors` 既保证列序，也让 CSV 可追溯。
